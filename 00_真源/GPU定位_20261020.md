# GPU 定位与资产账（2026-10-20）

> 结论先行（2026-10-20 E3209 更新）：**GPU 排序路径已真实可用并验证**（Adreno 829），但 **性能不优于 numpy**（1e7: 397.7ms vs 183ms）⟹ **不扩大深化**；保留为**宿主侧可选实验/纯 Python 大排序的备选**，压缩 backend 仍**不可复现=退役候选**，不新增仓库消费者。

## 〇、E3209 新结论（覆盖下方"不可用"旧判断）

- 通过 **Termux 宿主 bash** 调 `gpu_sort/run_gpu.sh`，**真实 GPU 可用**：`GPU: Adreno (TM) 829`；
- 补写缺失 `count16.comp`（自写直方图 shader），修 3 个正确性 bug：①紧凑桶槽宽 256→**512**；②pad 空槽必须填 **0xFFFFFFFF**（否则升序后有效项被挤到窗口尾、输出全 0）；③key 去掉 `^0x80000000`（unsigned 口径与 CPU 对拍一致）；
- **对拍**：n=1e6 输出与 `numpy.sort(uint32)` **逐元素相等**（perm=True · sorted=True）；n=1e7 内部校验 **正确=YES**；
- **基准**：n=1e5 59.9ms · n=1e6 157ms · n=1e7 **397.7ms**；CPU numpy 1e7 **183ms** ⟹ **GPU 排序正确但比 numpy 慢**（128MB pad memset + CPU 前缀/紧凑是瓶颈）；
- 结论：**不追求"用上 GPU"式的深化**；只在"纯 Python 大排序"且 numpy 不可用的场景值得作为备选；压缩 backend 仍因宿主源缺失不可复现。

## 〇·二、"找现成的"调研结论（E3211，2026-10-20）

> 用户令：「要不去找找有什么能用的，自己写一个的话，我觉得一些系统上不会太好」⟹ 只找**现成实现**，不自写 codec。

| 候选 | 许可 | 平台 | 实测/结论 |
|---|---|---|---|
| **gdeflate-benchmark**（Vulkan GLSL 解压 shader + host） | **MIT** | Vulkan/Android | ✅ **在 Adreno 829 上编译并跑通**：64MB 数据 CPU 压缩 → 286,744 B，**GPU 解压正确=YES**；GPU 64MB 解压 **9.9ms（~6.8 GB/s）** |
| **VolcanStorage**（GDeflate.comp，NVIDIA/Microsoft 移植） | Apache-2.0 shader | Vulkan | `glslc` 可编译 `GDeflate.comp`；整体工程偏 Windows/Linux，未在 Android 全量构建 |
| **lz-vk**（Rust/ash，自称 Termux/Adreno） | MIT | Vulkan | ❌ **WIP**：`compression/decompression` 模块全是 `pub fn add` 占位，不可用 |
| **gdeflate-rs** | MIT/Apache | CPU | 可用作 **GDeflate CPU compressor** 备选 |
| nvcomp / dietgpu | 各自 | **CUDA only** | Adreno 不可用 |
| brotli_g_sdk | MIT | **DX12/HLSL** | Adreno/Vulkan 不可用 |

**关键事实**：现有可移植实现里，**没有"GPU 压缩"**——GDeflate 是 **CPU 压缩 + GPU 解压**；GPU 压缩只有 CUDA 系（nvcomp/dietgpu），Adreno 用不了。
**结论**：①若未来要压缩能力，**直接用 GDeflate 栈**（MIT 的 benchmark shader/host + NVIDIA libdeflate），不再自写；②本仓数据管线在 CPU 侧，GPU 解压仍无消费者 ⟹ **暂不接线**；③参考包落 `/sdcard/Download/gpu_refs/`（README 含 URL/许可/实测）。

## 〇·三、GPU 到底"能算快什么"（E3212 实测，Adreno 829）

> 一句话：**GPU 是"带宽机器"**——大数组的**逐元素/归约/排序/扫描**远快于纯 Python；但**矩阵乘打不过 OpenBLAS**，**符号/Lean 完全不适配**。

| 负载 | GPU (Adreno 829) | CPU (同机) | 结论 |
|---|---|---|---|
| copy 128MB | **53.0 GB/s** | 4.5 GB/s (numpy 赋值) | **≈12×** |
| axpy 64MB | **57.0 GB/s** | 6.6 GB/s (numpy) | **≈9×** |
| 排序 1e6 uint32 | 157 ms（含 pad 填充） | pure Python `sorted` 470 ms | **≈3×**；但 numpy 33 ms ⟹ 比 numpy 慢 |
| 排序 1e7 uint32 | 397 ms | pure Python 5.39 s | **≈13.6×**；numpy 183 ms ⟹ 比 numpy 慢 |
| matmul 1024² fp32（naive tiled） | 62 GFLOP/s | **125–137 GFLOP/s**（OpenBLAS） | GPU **不占优**（需优化库才有戏） |
| GDeflate 解压 64MB | 6.8 GB/s | 10.6 GB/s（libdeflate） | CPU 更快（GPU 只在数据驻 GPU 时有意义） |

**由此得到的适用面**：
1. ✅ **大数组逐元素/归约/归一化/扫描/排序**——只要 CPU 侧是 **纯 Python 循环**，GPU 有 3–13×；与 numpy/BLAS 比则要看具体算子；
2. ✅ **GPU-resident 数据管线**（解压完直接在 GPU 用）——免回读；
3. ❌ **符号/Lean/ACL2/SAT**——标量与分支为主，GPU 无收益；
4. ❌ **小数组（n<10^5）**——launch/传输开销吃掉收益（排序 1e5 的 GPU 60ms 已含固定成本）；
5. ❌ **矩阵乘 vs OpenBLAS**——naive shader 慢一倍；除非用成熟 GPU BLAS（Adreno 上无现成）。

**本仓可接的真实候选**（按收益排序）：
- **排序**：`组件/sort_channel.py` 的纯 Python 路径（n≥1e6 时 GPU 3–13×）⟹ 可做**可选 GPU channel**（verify+门控，默认关）——**T-327**；
- **逐元素/归一化**：NN 数据导出/特征重算（当前数据量小，等有 10^7 级数组再接）；
- **FEM/粒子**：`fem2d` 网格更新/`chaos_sim` 粒子对撞（chaos 已有 C 扩展，且碰撞是数据相关顺序语义，GPU 改造风险高）——暂不接。

## 〇·四、GPU 常驻排序原型（E3213，"存算一体"软件形态）

> 不是硬件 PIM（手机没有），而是**软件层数据驻留 + 计算就地**：数据 load 一次后驻 GPU 缓冲，反复排序不再搬运；CPU 只做 65536 前缀和与按需 dump。

实现：`gpu_sort/gpu_resident.c` + `fill.comp`（哨兵/count/wpos 清零）+ `compact.comp`（GPU 紧凑），把原先 CPU 的 **128MB memset + 40MB 紧凑 memcpy + 65536 循环** 全部下放 GPU。

实测（Adreno 829）：
- n=1e7：首次 248ms，**10 次常驻排序平均 103.7ms/次**，正确=YES；总 CPU（user+sys）0.46s / 10 次 ≈ **46ms CPU/次**；对照一次性 `run_gpu.sh`：351ms/次、CPU ~0.6s/次；
- n=1e6：3 次平均 79ms，输出与 `numpy.sort` 逐元素相等；
- 结论：**常驻形态确实降低 CPU 压力**（CPU 只做编排+小前缀和），排序吞吐也优于一次性桥接；下一步是做成**常驻 daemon 服务**（跨进程复用缓冲，T-329）。

## 〇·五、常驻 daemon v1（E3214，T-329/T-327 落地）

- 协议：**文本行命令**（非 JSON）`LOAD <path> <n> <chunk>` / `SORT` / `DUMP <path>` / `STATS` / `EXIT`；命令/结果**原子 rename**；daemon 轮询 5ms；**命令文件只传小指令**，数据驻 GPU。
- 护栏：`vkWaitForFences` **5s 超时 ⟹ exit(3)（fail-closed）**；客户端结果超时杀 daemon（`/proc/<pid>/comm` 精确匹配，避免 pkill/pgrep 误杀自身）；启动用 STATS 握手探针。
- 实测（Adreno 829，客户端在 PRoot）：
  · **10M 数据**：LOAD 40MB（8MB 分包）0.04s；**首次排序 407ms，之后 81ms/次**；客户端总延迟 **95ms/次**；dump/verify（保序+和/xor 指纹）通过；
  · **1M**：首次 94ms，稳态 GPU **61ms**，客户端 **76ms**。
- `sort_channel` 接入（T-327）：`LK_GPU_SORT=1` 且 n≥1e6 才走 `gpu_resident` channel；验证=单调性+和/xor 指纹；失败回退 C/Python。实测一次调用首启 3.0s（含 daemon 启动/文件 I/O），**同数据重复 0.203s vs C radix 0.638s** ⟹ 默认关，只在"驻留重复算"有意义。
- 下一跳 **T-330**：把**压缩包分片**接进 daemon（CPU 按块压 → GPU 逐包解压到常驻缓冲；GDeflate 栈已有 Adreno 实测），实现真正的"分包一点一点跑过去"。

## 〇·六、自适应桶位数（E3219）：1M 61ms→12ms，10M 81ms→56–60ms

- 旧实现固定 **16 bits 桶 × 512 槽** = 33.5M pad 槽，bitonic 固定成本与 n 无关（1M 也要 60ms）。
- 新实现按 n 选桶位数：`avg+5σ<500`（bits 8..16）；1M→**12 bits**（4096 桶），10M→**15 bits**（32768 桶）。
- 实测（Adreno 829，稳态）：
  · **1M**：总 **11.7ms**（bitonic 4.3ms）· 客户端 **22ms**；
  · **10M**：总 **56–60ms**（bitonic **34–35ms** · scatter 9.5 · count 6.8 · fill 2.6 · compact 2）· 客户端 **65–78ms**；
  · 正确性：dump 后与 numpy 对拍/指纹通过。
- 剩余固定成本：①bitonic 仍占 60% ⟹ 下一步**桶内计数排序/Radix**（T-332）；②首次 LOAD 后首单仍 ~250ms（scatter ~190ms）——怀疑 CPU 写 host-visible 后 GPU 首次随机写/一致性开销 ⟹ **staging/device-local 缓冲**（T-331）；③IPC 约 10–18ms ⟹ 共享内存（T-333）；④本环境 `/sys/class/thermal` 只有 cooling_device、无 thermal_zone ⟹ 温控需 `termux-battery-status`/dumpsys 另找入口（T-334）。

## 〇·八、对旧档（E3223）：GPU 的真分区是"n≥4M 高基数"，不是小数据/低基数

旧档（同机实测，`大规模冠军切换_8M-64M_20260908.md` / `排序_融合基准_20260920.md` / `排序_测量台账`）：
- C **radix8q 是 8M–64M 冠军**：8M **64.9ms** / 16M **167.5ms** / 32M **342.6ms** / 64M **673.5ms**，吞吐 8M 后 **~95M/s 平台**（带宽受限，非算法）；
- 小数据 C 极强：random 100k **0.41ms** · 1M **11.2ms** · 4M **46.2ms**；dup 100k **0.09ms** · 1M **2.3ms** · 4M **8.9ms**；
- 形态敏感度：radix8q 1.5× 最鲁棒；counting/run_merge 专精；int64 约 **1.6×**；结构化/argsort **25–35×**。

本机 GPU 补充（resident daemon，稳态；证书见矩阵）：
| n | GPU | 旧档 C 冠军 | 判定 |
|---|---|---|---|
| 100k | 7–10ms | 0.41ms | C **17–20×** |
| 1M | 15–17ms | 11.2ms | C 约 1.4× |
| 4M | **27–30ms** | 46.2ms（sort_v6；radix8q 约 33–46） | GPU **1.5×**（对 radix8q 约 1.1–1.2×） |
| 8M | **52.5ms** | 64.9ms（radix8q） | GPU **1.22×** |
| 16M | **103ms** | 167.5ms（radix8q） | GPU **1.63×** |
| 1M dup | 28ms（回退） | 2.3ms（C dedup） | C **12×**，不追 |

结论：**GPU 只该接 n≥4M 高基数分区**；小数据/低基数让 C；用户"降 CPU 压力"目标下，4M 时 GPU CPU 侧约 14ms vs C 46ms，仍值得作为**卸载通道**。
首单 LOAD 后仍有尖峰（8M 266ms、16M **1192ms** vs 稳态 103ms）⟹ **T-342** staging/device-local。
旧档还纠正了基准选择：`v6(array) 10M=1599ms`（勘误后），**不能用 numpy/v6 当冠军基线**，必须对 C radix8q。

## 〇·九、基准假象与 fresh 修正（E3224）：8M/16M 之前是"排已排序数据"的假快

**发现**：旧矩阵每轮 `SORT` 不重载，第 2/3 轮输入已被排好；GPU 对有序输入 scatter 是顺序写，所以 8M 52ms/16M 103ms 是**假快**。
**每轮重载 fresh 后（只计 SORT）**：
- 1M random **11.9–14.3ms** vs C 11.2ms ⟹ 基本打平（C 略优）；
- 4M random **34.9ms** vs C 46.2ms（sort_v6；radix8q 约 32–46）⟹ 打平/略优；
- **8M random 263ms vs C radix8q 64.9ms ⟹ GPU 输 4×**；
- **16M random 821ms vs C 167.5ms ⟹ GPU 输 4.9×**。
**根因**：不是首单缺页（UMA 内存类型、pad 全量 CPU memset、GPU fill 预热都试过仍 scatter 163ms@8M / 920ms@16M）；而是 **pad 工作集 >32MB 后随机 scatter 写带宽崩溃**（4M pad 33MB / 8M 67MB / 16M 128MB）。
**结论**：当前单趟 MSD pad 算法只适合 ≤4M；8M+ 必须 **多趟 radix / tiled-coalesced scatter**（T-344）。旧 T-341“8M/16M 赢”作废、重开。

## 〇·十、紧凑散射（T-344）：8M 以下真赢，16M 仍撞 64MB 随机写墙

**实现**（T-344 原型）：
- `scatter_compact.comp`：桶区间连续输出到 **n 级缓冲**（不再写 65536×512 的 pad，随机写工作集从 128MB 降到 n×4）；
- `bitonic_var.comp`：每桶 workgroup 共享内存排序，桶长 ≤512（host 的 avg+6σ<450 保证）；
- offsets 复用 count 缓冲（桶数+1），wpos 只做桶内游标。

**fresh 输入实测（每轮 LOAD，只计 SORT；证书=有序+和/xor 对账）**：
| n | 结果 |
|---|---|
| 1M | 7.0–13ms（C 11.2）⟹ **持平/略优** |
| 4M | 25–40ms（C 46.2；radix8q 约 32–46）⟹ **GPU 1.2–1.8×** |
| **8M** | **52–74ms（C 64.9）⟹ GPU ~1.0–1.25×（真赢）** |
| **16M** | **454–687ms（C 167.5）⟹ 仍输 2.7–4.1×**（scatter 382–610ms） |
| 100k | 11–24ms（C 0.41）⟹ C 完胜 |
| 1M dup | 16.6ms GPU（C 2.3）⟹ C 仍胜；few_uniq 回退 CPU |

**结论**：紧凑散射把 8M 从 263ms 修到 ~52–74ms，**8M 及以下已可与 C 打平/略优**；16M 的 64MB 输出随机写仍是墙 ⟹ 需 **分块排序 + k 路归并（kmerge2）** 或 tiled scatter（T-346）。
**生成器速度**（顺带量）：`search_best_algorithm` 20 候选 **0.033s**、`search_fast` 50 候选 **0.027s**；`sort_gen_deep.py 2代×5种群 n=500` **3.74s**（≈1.8s/代）。**生成/搜索很快；但生成算法是纯 Python，执行速度不具生产意义**（旧档：纯 Python vs C 标准库 ~98×），其价值是搜索/覆盖，不是速度。

## 一、早期事实（历史，部分已被上节修正）

1. **执行环境是 PRoot**（`uname` = `...-PRoot-Distro`）：无 `/dev/dri`、无 OpenCL/Vulkan 设备；`gpu_sort/README_GPU.md` 明言 GPU 只能在 **Termux 宿主（proot 之外）**用。
2. **Vulkan radix 当前不可从仓内编译**：`vulkan_radix_sort.c` 需要 `count16.spv`（源 `count16.comp`），但仓里**没有 `count16.comp`**；`run_gpu.sh` 却引用它。
3. **压缩 backend 不可复现**：`组件/compress_gpu_backend.py` 声称 123×（Adreno 829, n=1e7），但它依赖宿主二进制 `vk_compress`；该二进制的**源码/构建脚本不在仓**，`run_gpu.sh` 的 `compress` 分支也**不存在**。
4. **零仓库消费者**：`gpu_sort` 与两个 backend 只被自身/注册件引用；链路与体检都没有消费 GPU 结果。
5. **重复所有者/死件**：`run_gpu_host.sh` 与 `gpu_sort/run_gpu.sh` 同内容；OpenCL 版（`gpu_radix_sort.c`/`radix_sort.cl`）与 Vulkan 版二选一；`.bak` 未归档；`gpu_daemon_v2.sh` 含 `eval` 任意命令通道（只应宿主本地用）。

## 二、为什么"深化"优先级低

- 本仓瓶颈是 **Python 启动/自测（20s→3s 已修）· sympy/Lean · 缓存未命中**，不是大数组数值吞吐；
- GPU 赢面要求 **n≥10^5 的数值数组**（backend 自己 `MIN_N=100000`）；当前热路径没有这种负载；
- 数学/Lean/解析是 CPU/标量负载，搬 GPU 无收益；
- 跨 PRoot/宿主文件桥 + 自定义格式，维护成本高、验证面窄。

## 三、改革方案（建议执行）

| 处置 | 对象 | 理由 |
|---|---|---|
| **保留（宿主可选）** | `vulkan_radix_sort.c` + `scatter16.comp`/`bitonic.comp` + `gpu_daemon_v2.sh` | 唯一"全程 GPU"实现；但**必须先补 `count16.comp`** 并宿主复测 |
| **退役/归档候选** | OpenCL 重复（`gpu_radix_sort.c`/`radix_sort.cl`/`cl_test_nohdr.c`）· `README_GPU.md.bak` · 根 `run_gpu_host.sh` 重复 |
| **标"不可复现"** | `compress_gpu_backend.py` / `register_gpu_compress.py` | 宿主源缺失 ⟹ 不得当可用 backend；要么补源，要么退役 |
| **保留契约、零消费者** | `sort_gpu_backend.py` / `sort_with_gpu.py` | 可选 backend 契约；不进链、不当默认 |
| **不新增** | 任何 GPU 消费者/链路 | 直到出现 `n≥10^5` 且 CPU 是瓶颈的真实热路径 |
